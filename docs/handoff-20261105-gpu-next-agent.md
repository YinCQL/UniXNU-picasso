## IR3 shader cache (the optimization in flight)

The plugin sets `MESA_SHADER_CACHE_DIR=<candidate>/mesa` before `native_bridge_metal_open`
(`UniXNU/drivers/NativeMetal/NativeAdrenoMetalPlugin.mm`); the runtime's m2v directory is exported by the plugin over
method 0x7100 as `SHEXR001`, stored by the kernel in the aux window at block 4096, and replayed at the apps-mount gate
before launchd (see `patches/picasso-ls-persist-xnu.patch`, `PICASSO_M2V …`).

First wf292 boot:

- import: `PICASSO_M2V dir files=1144 bytes=16360988` → `PICASSO_M2V import files=0 skipped=1144` (all already matched)
- export grew during the boot: `total=16553552 blocks=4043`, then `total=16857490 blocks=4117`
  → the mesa cache is being written and rides the SHEXR001 stream.

Next (the pending acceptance test):

1. Boot the same wf292 image a second time. Expect `PICASSO_M2V import files=N` with N > 0 (the mesa files written)
   and an export that converges near the previous total. Record the SpringBoard GPU-open/first-present time of the
   second boot — that is the metric, not cache-hit counts.
2. For an A/B, rebuild a publish addon from a plugin build without the IR3 change (or disable the env var) with the
   same kernel and compare first-present/compile time. One variable per image.


Back to fastboot from userspace: inject `reboot-fastboot` through the capture tool
(`--send reboot-fastboot --send-after 3 --duration 75`). The port open/config takes ~37 s, so short capture windows
never reach the send (the command silently does nothing). CDC commands (`ps`, `snapshot`, `save-ls`, `ls-scan`,
`reboot-fastboot`) are only injected through the capture tool; the serial port is exclusive.

Useful log greps: `PICASSO_GPU open: plugin`, `code signature validation failed`, `PICASSO_M2V (dir|export|import)`,
`PICASSO_GPU submits`, `PICASSO_DISPLAY_STATE`, `PICASSO_PS`.
