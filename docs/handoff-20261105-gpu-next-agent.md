## IR3 shader cache (the optimization in flight)

The plugin sets `MESA_SHADER_CACHE_DIR=<candidate>/mesa` before `native_bridge_metal_open`
(`UniXNU/drivers/NativeMetal/NativeAdrenoMetalPlugin.mm`); the runtime's m2v directory is exported by the plugin over
method 0x7100 as `SHEXR001`, stored by the kernel in the aux window at block 4096, and replayed at the apps-mount gate
before launchd (see `patches/picasso-ls-persist-xnu.patch`, `PICASSO_M2V …`).

First wf292 boot:

- import: `PICASSO_M2V dir files=1144 bytes=16360988` → `PICASSO_M2V import files=0 skipped=1144` (all already matched)
- export grew during the boot: `total=16553552 blocks=4043`, then `total=16857490 blocks=4117`
  → the mesa cache is being written and rides the SHEXR001 stream.

Next (the pending acceptance test):

1. Boot the same wf292 image a second time. Expect `PICASSO_M2V import files=N` with N > 0 (the mesa files written)
   and an export that converges near the previous total. Record the SpringBoard GPU-open/first-present time of the
   second boot — that is the metric, not cache-hit counts.
2. For an A/B, rebuild a publish addon from a plugin build without the IR3 change (or disable the env var) with the
   same kernel and compare first-present/compile time. One variable per image.

**Verified results.**

- IR3 cache on the wf292 second boot: `PICASSO_M2V dir files=1154 bytes=16674043`,
  `import files=0 skipped=1154`, export converged to `total=16868211 blocks=4120`; telemetry
  `V cache hit49 miss0` and `V vkpipe n=49 total=118ms`. The cache is effective (all hits), and it
  keeps growing as new UI variants appear (18,413,808 B / 4497 blocks after the wf298 animation).
- Frame timing (wf292/298): idle frames present in 9.8 ms (import 44 µs, encode+commit ≈ 6 ms CPU,
  GPU wait ≈ 2.5 ms); the idle 100 ms interval is the lock-screen clock's own cadence. During the
  SpringBoard startup animation, present rises to 33.8 ms, of which the **GPU wait is 26–33 ms** —
  animation is GPU-bound, not CPU-bound. This refines GPU优化.txt: the GPU is idle on average but
  saturated during every animated interval.
- USB: the CDC descriptor now asks for 500 mA instead of 200 mA
  (`patches/picasso-usb-console-xnu.patch`); macOS reports `UsbPowerSinkAllocation = 500` (2.5 W).
- Speed bin: this unit reports `bin=84` in the HFI log, table 625/500/400/275 MHz. Default perf
  index 3 = 500 MHz; index 4 = 625 MHz (the bin's top). `sheng-gpu-perf-index=7` is out of range
  and silently ignored (prints `boot index=7 nominal`). Use index 4 for clock A/Bs.
- Synthetic touch: swipes publish and reach `IOHIDEventDriver` (`moved=1`, +26 reports,
  dispatch=26/26) but the lock screen does not act on them, while a physical finger works — a
  touch-path issue, not the GPU; see `picasso-synthetic-touch-not-consumed` in the session memory.
  Do not trust `moved=1` as evidence of a working gesture; require a `PICASSO_FRAME` burst.

**Operational notes.**

- The 5-minute battery budget is counted **from the lock screen**, not from boot; a capture may run
  ~9 minutes total (boot ~4–5 min + 5 min of UI).
- Start the CDC capture before `fastboot boot`; opening a stale port later triggers a gadget reset
  and the capture misses everything. If the device stays booted past the window, a raw
  `os.open` + drain + `reboot-fastboot` write (no modem-line changes) reliably returns it to
  fastboot.
- `scripts/build-wf-payload.sh` strips `offline-hid-swipe=16` from `board.toml`; pass swipe args as
  extra kernel arguments.

### Deferred completion is now the present default (wf307/wf308)

`GpuScanoutPresenter` no longer waits for the scanout blit inside `present`: it commits and returns,
and the **next** present settles the previous frame's completion without blocking
(`settle()`), with the same 400 ms bound and three-timeout cooldown as before. A wedge is still
caught and the display driver still gets its own path, one frame later. The first frames' CPU
verification calls `flush()` so the readback still sees completed pixels.

Same-binary A/B on hardware: burst service **7.4 ms** deferred vs **9.8 ms** with
`sheng-present-blocking=1` (which restores the old wait); PF wait 0 vs 2.29 ms; burst cadence 33.0
vs 32.9 ms; failures 0; verification `v4/0`; CPU fallbacks (`copies=0`). `sheng-present-nonblock=1`
still selects the never-settle variant.
